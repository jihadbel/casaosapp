## 2. النتيجة التنفيذية

المشروع قابل للتنفيذ فوق الخادم الحالي. الجزء الأكبر من العمل هو بناء عميل Flutter فعلي، مع استكمال عقود محددة في الخادم، خصوصاً متابعة النسخ والنقل، والبحث المتكرر، وتصفح المجلدات الكبيرة. وثيقة SRS جيدة لتحديد تجربة المنتج، لكنها تحتاج ملحق توافق قبل اعتماد جدولها البرمجي.

الأولوية المقترحة هي Android وWindows كأول منصتين للتجربة، مع إدخال اختبارات توافق iOS وmacOS في مرحلة مبكرة، ثم تسليمهما ضمن مسار الإصدار الكامل عند توفر Mac وأجهزة الاختبار. جميع متطلبات الوثيقة تبقى ضمن الخطة الكاملة؛ تقسيم التسليم هنا اقتراح لتنظيم العمل.

### الوضع الحالي للتطبيق

- عند بدء الفحص كان `lib/main.dart` يشغّل تطبيق العدّاد الافتراضي فقط.
- أثناء المراجعة ظهرت ملفات `core/theme/` و`core/models/` ثم مجموعة شاشات في `lib/screens/`، وأصبح `main.dart` يشغّل `CasaOSApp` بواجهة عربية. أُضيفت `intl` و`flutter_localizations` إلى الاعتمادات.
- الشاشات الحالية نموذج واجهات يمكن إعادة استخدامه: الدخول والاكتشاف يحاكيان الاستجابة بواسطة `Future.delayed`، والملفات والنقل والإدارة تعتمد `MockData`. لا يوجد في الملفات المفحوصة عميل API أو مصادقة أو محرك نقل حقيقي.
- بيانات العرض تتضمن صوراً من Unsplash، وشاشة الدخول تتضمن قيمة كلمة مرور تجريبية معبأة مسبقاً. يُستبدل ذلك بأصول محلية وحقول حساب حقيقية عند الربط، لاستيفاء الخصوصية وعدم الاتصال بخدمات خارجية.
- نموذج الملف الحالي يعتمد على Flutter والألوان والأيقونات. يمكن الاحتفاظ بوظائف العرض، مع فصلها عن الكيان المستقل ونموذج JSON عند ربط البيانات.
- المسارات والهويات في `MockData` تجريبية؛ الخادم يستخدم مجلداً مرتبطاً بمعرّف ثابت للحساب، ولا يجوز توليد مسار المستخدم من اسمه.
- لم يوجد مستودع Git في مسار التطبيق عند الفحص. حفظ نقطة بداية ومراجعة التعديلات الجارية جزء من مرحلة التأسيس المقترحة.

### الوضع الحالي للخادم

- يدعم الوضع المستقل الحسابات المحلية، وجلسات الكوكي، وإدارة المستخدمين وإلغاء الجلسات عند تغيير كلمة المرور أو تعطيل الحساب.
- يعزل الملفات والإعدادات والسلة والمعرض داخل مجلد كل مستخدم؛ المسؤول يخضع لحدود الملفات نفسها.
- يوفر عمليات الملفات، ورفع الأجزاء مع فحص وجود الجزء، وتنزيل الملفات مع `Range` عبر `http.ServeContent`، والسلة، وZIP، والخط الزمني، ومحرر النصوص.
- يمنع في الوضع الخاص واجهات مثل الأقراص وSMB وWebSocket وميزات إدارة النظام القديمة؛ وجود المسار في الموجّه العام لا يعني إتاحته للعميل المستقل.
- ملف `api/casaos/openapi.yaml` يصف واجهات V2 الأصلية ولا يغطي عقد العميل المستقل `/api/*` و`/v1/*` تغطية صالحة لتوليد SDK مباشرة.

## 3. الفجوات والتصحيحات المطلوبة في SRS

| البند | ما ثبت من المصدر | أثره على التنفيذ |
|---|---|---|
| إصدارات Flutter والحزم | البيئة المحلية Flutter 3.47.1 وDart 3.13.1؛ الوثيقة تقترح Flutter 3.24 وحزماً أقدم | اعتماد SDK المحلي بعد تثبيت توافق الحزم، وعدم نسخ أرقام إصدارات الوثيقة تلقائياً |
| طبيعة كوكي الجلسة | `casaos_session` رمز عشوائي، والجلسات محفوظة في ذاكرة الخادم لمدة 12 ساعة | ليست كوكي مشفّرة ذاتياً؛ تشفير النقل يأتي من HTTPS. إعادة تشغيل الخادم تُبطل الجلسة المحفوظة على الجهاز |
| Origin | `sameOrigin` يقبل غياب `Origin` و`Sec-Fetch-Site`، ويرفض Origin المختلف أو `cross-site` | عميل native لا يحتاج محاكاة ترويسات المتصفح؛ إن أُرسلت Origin فتشمل البروتوكول والمضيف والمنفذ بدقة |
| معلومات الجلسة | GET يعيد `user` كنص و`home` و`privateStorage`؛ POST الناجح يعيد `authenticated` فقط | طلب GET بعد الدخول ضروري. يوصى بإضافة `userId` و`admin` صراحة إلى العقد |
| قراءة النص | `/v1/file/content` يعيد JSON يحتوي النص في `data` | لا يُقرأ الرد كنص خام كما في جدول الوثيقة |
| تاريخ الملف | `date` و`modified` حقول Go `time.Time` بصيغة نصية RFC3339 | مثال Dart الذي يحوّل `date` من Unix seconds غير متوافق |
| الصور المصغرة | الفرع المصغّر يعمل عند `type=thumbnail` | `type=preview` الوارد في جدول الوثيقة يعود لمسار الأصل وقد ينزّل صورة كبيرة |
| استعادة السلة وحذف عنصرها | الحمولة الفعلية `{"id":"..."}` لعنصر واحد | `{"paths":[...]}` غير صحيح؛ المعالجة الجماعية تحتاج نتائج مستقلة لكل عنصر أو API جديدة |
| استجابة الحسابات | `/api/users` يعيد `{"users":[...]}`؛ السجلات تتضمن `id, username, admin, disabled, created` | ليست مصفوفة مباشرة، ولا يتضمن سجل الإدارة `homePath` لكل حساب |
| النسخ والنقل | POST يضع العملية في طابور ثم يعيد نجاح قبولها دون معرّف المهمة | لا يجوز عرض «اكتملت» عند HTTP 200. المتابعة والإلغاء يتطلبان واجهة مهام مرتبطة بمالكها |
| تصفح المجلدات | توجد حقول index/size في النماذج، لكن `DirPath` لا يربطها من الاستعلام ويستخدم افتراضياً 100000 عنصر | لا توجد صفحات فعلية يمكن للعميل الاعتماد عليها؛ يلزم تصحيحها للأحجام الكبيرة |
| البحث المتكرر | واجهة البحث القديمة غير متاحة عبر بوابة الملفات الخاصة | بحث المجلد الحالي يمكن محلياً؛ البحث في الشجرة يحتاج API معزولة أو مسحاً محدوداً معلناً للمستخدم |
| اكتشاف الخادم | لم يظهر ناشر mDNS في كود Go المفحوص | مكتبة الاكتشاف في الهاتف وحدها لا تضمن العثور على الخدمة؛ الإدخال اليدوي أساسي، ونشر الخدمة عمل إضافي |
| معلومات الخادم | `/api/server-info` يعيد عناوين الشبكة، و`/v1/sys/utilization` يعرض موارد الجهاز | لا توجد حصة تخزين شخصية أو إحصاءات مكتبة المستخدم أو قائمة ملفات أخيرة عامة جاهزة |
| الخط الزمني | يدعم `limit/offset/type` و`has_more/truncated`، ويقيد المسح بـ2000 وسيط و50000 مدخل و5 ثوانٍ | يجب بيان النتيجة الجزئية؛ تحميل صفحات الرد لا يعني فهرسة المكتبة كلها |
| تاريخ التصوير | التجميع الحالي مبني على وقت تعديل الملف | عرض «تاريخ التصوير» يحتاج EXIF/فهرسة إضافية، أو تسمية التاريخ الحالي بدقة |

| تنزيل عدة مسارات | `GET /v1/batch` يفصل المسارات بفاصلة | اسم ملف يحتوي فاصلة يسبب التباساً. يستخدم مسار منفرد أو ZIP عبر JSON، أو يضاف عقد تنزيل جماعي جديد |

| البيانات التجريبية الجديدة | الشاشات تستخدم MockData ومحاكاة الدخول وصور Unsplash | فصل وضع العرض عن التشغيل الفعلي، وعدم اعتماد واجهة جاهزة دليلاً على اكتمال الميزة |

## 4. عقد التكامل الذي يُثبت أولاً

### العقد الحالي المؤكد

| المجال | الطلب الصحيح | الاستجابة أو القيد المهم |
|---|---|---|
| فحص الخادم/الجلسة | `GET /api/auth/session` | `200` و`authenticated:false` حالة طبيعية قبل الدخول؛ ليست خطأ اتصال |
| الدخول | `POST /api/auth/session` مع `username,password` | حفظ `Set-Cookie` ثم GET للجلسة وGET للإعدادات |
| الخروج | `DELETE /api/auth/session` | إنهاء الجلسة على الخادم ومسح حالتها محلياً |
| كلمة المرور | `POST /api/auth/password` مع `password` | طول 12–72 بايت UTF-8؛ يُبطل جلسات الحساب، فتظهر شاشة إعادة الدخول |
| الملفات | `GET /v1/folder?path=...` | غلاف V1: `success` عدد، `message`، و`data.content/total/index/size` |
| حفظ النص | `PUT /v1/file` مع `path,content` | دعم ملف أصلي حتى 16 MiB، مع المحافظة على الترميز ونهايات الأسطر في الخادم |
| رفع الأجزاء | `POST /v1/file/upload` بصيغة multipart | الحقول: `path,file,filename,relativePath,totalChunks,chunkNumber,uploadId`؛ ترقيم الأجزاء يبدأ من 1 |
| فحص جزء | `GET /v1/file/upload` مع بيانات الجزء نفسها في الاستعلام | `200` للجزء الموجود، `204` لغير الموجود، `409` لتعارض الملف النهائي |
| التنزيل الفردي | `GET /v1/file?path=...` مع `Range` عند الاستئناف | التعامل مع `200/206/416` والتحقق من `Content-Range`؛ لا يُلحق رد 200 بملف جزئي |
| المصغرات | `GET /v1/image?path=...&type=thumbnail` | فشل المصغرة لا يعني حذف الأصل؛ يلزم عنصر بديل في الواجهة |
| المعرض | `GET /api/media/timeline?type=photos&limit=100&offset=0` | `limit` حتى 200؛ دمج المجموعات حسب `key` وتوطين عنوان الشهر في العميل |
| السلة | GET للسلة، وPOST للاستعادة/حذف العنصر مع `id` | استعادة إلى اسم موجود تعيد `409`؛ لا يجري الاستبدال التلقائي |
| الأرشفة | `POST /api/zip` مع `files,output`؛ `POST /api/unzip` مع `path,dest` | حدود الحجم والعدد تُعرض عند الفشل، وتلغى الطلبات عند إلغاء المستخدم |
| المسارات القياسية | `GET /api/settings` ثم `settings.*Path` | الاعتماد على القيم التي يعيدها الخادم؛ الجذر الخاص ثابت |

استجابات `/api/*` وV1 مختلفة؛ لا يحوّل العميل `success:200` إلى boolean، ولا يفترض أن كل استجابة ناجحة تحمل `data`. تُوثّق حالات `400,401,403,404,409,410,413,415,429,5xx` لكل عملية، مع إيقاف إعادة محاولة تسجيل الدخول آلياً.

## 5. المعمارية المقترحة للتطبيق

اعتماد تنظيم Feature-First، مع فصل العرض عن البيانات وقواعد العمل. تضاف الواجهات المجردة حول موارد لها أثر فعلي: الاتصال، التخزين الآمن، الملفات، النقل، الوسائط، والخلفية. لا تُنشأ طبقات إضافية لكل دالة بسيطة.

```text
lib/
  app/                    bootstrap, router, localization, adaptive shell
  core/
    network/              HTTP client, error mapping, server compatibility
    security/             session vault, certificate trust, app lock
    storage/              local database, migrations, scoped cache
    platform/             file handles, background transfers, media access
    theme/                colors, typography, light/dark themes
    widgets/              shared presentation components
  features/
    connection/           manual server entry, saved servers, discovery
    auth/                 session, login, password, account switcher
    home/                 quick folders, usage, recent activity
    files/                browsing, search, selection, operations
    transfers/            persistent queue, upload/download executors
    gallery/              timeline, thumbnails, image viewer
    media/                authenticated video/audio, background playback
    documents/            PDF viewer, text editor
    trash/                listing, restore, permanent deletion
    admin_users/          accounts and server metrics
    auto_backup/          media selection, indexing, sync policy
    settings/             appearance, connection, privacy, backup settings
```

| قفل التطبيق | local_auth مع fallback إلى مصادقة الجهاز | التحقق من سلوك Windows Hello وعدم توفر بصمة على بعض الأجهزة: [توثيق local_auth](https://pub.dev/packages/local_auth) |
| الخلفية | منفذ مستقل عن Dio وواجهة المستخدم، مع تكامل نظام التشغيل | اختيار [جدولة workmanager](https://pub.dev/packages/workmanager) والنقل الطويل وفق [قيود Android](https://developer.android.com/develop/background-work/services/fgs/timeout) و[خلفية Apple](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app) |

أرقام حزم الوثيقة تُعامل كمرشحات تاريخية. تُضاف الاعتمادات عند الحاجة إلى الميزة، بعد تجربة صغيرة على المنصات المستهدفة، مع تسجيل الترخيص ومتطلبات النظام.

### قواعد الجلسة والعزل المحلي

1. مفتاح نطاق البيانات هو هوية الخادم والحساب الثابت؛ الأصل يتضمن `scheme,host,port`. تغيير الخادم أو الحساب يبدّل النطاق كاملاً.
2. لكل حساب حاوية كوكي وكاش وطابور مستقل. «تذكر الحساب» يحتفظ بالهوية والجلسة الآمنة، دون حفظ كلمة المرور افتراضياً.
3. تبديل الحساب يحتفظ بجلساته الأخرى وفق الإعدادات، ويوقف مهام الحساب السابق. تسجيل الخروج يمحو أسرار الحساب المحدد ومعايناته ومسوداته ونتائجه الحساسة.
4. تُلغى الطلبات عند التبديل أو الخروج، ويُستخدم رقم جيل للجلسة لمنع الردود المتأخرة من إعادة بيانات حساب سابق إلى الواجهة أو القرص.
5. حالات الجلسة واضحة: فحص، غير مسجل، مسجل، مقفول محلياً، منتهٍ. انقطاع الشبكة لا يحوّل تلقائياً إلى «كلمة مرور خاطئة».
6. تستمر حماية TLS الافتراضية. الشهادة المحلية تعتمد CA موثوقة أو بصمة مثبتة لهذا الخادم بعد التحقق منها، مع مسار واضح لتغييرها؛ لا يوجد قبول عام لكل الشهادات.
7. تنزيلات المستخدم التي اختار تصديرها تبقى ملفات يملكها على جهازه؛ يُميَّز ذلك عن كاش المعاينات الذي يُمسح عند الخروج.
8. القفل المحلي يحجب الواجهة والمحتوى في معاينة التطبيقات. استمرار النسخ الاحتياطي أثناء القفل إعداد واضح، ويتوقف دائماً عند الخروج أو إلغاء الحساب.
9. تحجب طبقة الاتصال تحويل الكوكي إلى أصل مختلف عبر redirect، ويُختبر ذلك أيضاً في المشغل ومنفذ الخلفية. لا تُسجَّل كلمات المرور أو الكوكي أو مسارات خاصة كاملة في سجلات الإنتاج.
10. مسار الخادم لا يعالج بواسطة مكتبة مسارات الجهاز المحلي؛ عميل Android قد يتعامل مع مسار Windows. تُفصل مسارات الخادم عن مسارات الجهاز.

## 6. تصميم محرك النقل قبل بناء واجهته

حالات المهمة المقترحة: `queued → running → completed`، مع `paused`, `waitingNetwork`, `waitingAuth`, `conflict`, `completionUnverified`, `failed`, `canceled`. تخزين الحالة بمعاملة مع بيانات الاستئناف يمنع ظهور مهمة مكتملة بلا ملف صحيح.

### الرفع

- يولَّد `uploadId` ثابت لكل عملية، ويُحفظ قبل أول طلب مع الحساب والوجهة والمصدر وحجمه وبصمته ووقت تعديله وحجم الجزء.
- يبدأ التنفيذ بجزء 8 MiB وتزامن ملفين كقيم أولية قابلة للقياس. قراءة الملف تتم كتدفق؛ لا يُحمَّل ملف 50 GiB في الذاكرة.
- قبل إرسال الجزء بعد الاستئناف، يُستخدم GET لفحص وجوده ببيانات الهوية نفسها. عند بقاء العملية داخل التطبيق، تُحفظ الأجزاء المؤكدة وتُراجع عند الشك.
- يحتفظ كل مصدر محلي بإذن وصول صالح بعد إعادة التشغيل: URI دائم على Android أو مرجع مناسب على Apple/سطح المكتب، أو نسخة مرحلية محسوبة المساحة.
- إذا تغيّر المصدر، تُطلب عملية جديدة. لا يُعاد استخدام أجزاء ملف قديم مع محتوى مختلف.
- `409` حالة تعارض تحتاج تفسيراً، ولا تثبت وحدها نجاح رفعنا. إذا انقطع رد الجزء الأخير بعد نشر الملف، تسجل المهمة `completionUnverified` حتى التحقق بنتيجة نهائية أو محتوى موثوق.
- الخادم ينظف الأجزاء المتروكة الأقدم من 24 ساعة؛ عند زوالها تُعاد الأجزاء الناقصة. الاستئناف ليس ضماناً لبقاء الأجزاء إلى أجل غير محدد.
- النجاح يعني اكتمال النشر على الخادم، ثم تحديث سجل المهمة والنسخ الاحتياطي، ثم تنظيف الملفات المرحلية.

### التنزيل

- تخزين الملف باسم مؤقت مع عدد البايتات ومعلومات التحقق، ثم طلب `Range` عند الاستئناف.
- الرد `206` يحتاج `Content-Range` مطابقاً؛ الرد `200` يبدأ الملف من جديد؛ `416` يحتاج إعادة تحقق من الحجم والنسخة.
- استخدام `If-Range` مع validator متاح، ورفض جمع أجزاء من نسختين مختلفتين. عند غياب ضمان كافٍ يعاد التنزيل بأمان.
- أرشيف ZIP الذي يولَّد كتدفق لا يُعامل كملف قابل لاستئناف عشوائي. يمكن إعادة توليده، أو إنشاء ZIP محفوظ وتنزيله كملف عند الحاجة.
- تُحسب مساحة القرص المطلوبة قبل بدء التنزيل أو تجهيز multipart للخلفية، مع تنظيف الملفات المؤقتة عند الإلغاء.

### سياسة المحاولات

إعادة محاولة محدودة ومتدرجة مع jitter لأخطاء الشبكة والعمليات الآمنة. لا تُعاد تلقائياً عمليات إنشاء الحسابات أو النسخ أو الحذف أو الأرشفة دون معرفة ما إذا نُفذت. `401` يوقف مهام الحساب لطلب الدخول، و`403` يوضح رفض الصلاحية، و`429` يحترم مدة الانتظار المتاحة.

## 9. ضوابط المنصات وتجهيز بيئة البناء

### ما ظهر في `flutter doctor -v`

- Flutter 3.47.1 / Dart 3.13.1 متاحان.
- Android SDK 37 موجود؛ حالة تراخيص SDK غير معروفة وتحتاج الاستكمال عند بدء البناء.
- أدوات Windows غير مكتملة: يلزم workload تطوير سطح المكتب بـC++ ومكونات MSVC وCMake وWindows SDK المناسبة.
- لم يظهر هاتف أو محاكي Android متصل؛ الأجهزة المتاحة وقت الفحص Windows وChrome وEdge.
- بناء iOS وتوزيعه يحتاج macOS وXcode وفق [توثيق Flutter](https://docs.flutter.dev/deployment/ios). تُجهز إمكانية الوصول إلى Mac قبل مرحلة الوسائط، مع هاتف iPhone لتجارب الخلفية.
- Android ما زال `com.example.casaosapp`، وتوقيع release يستخدم مفتاح debug. يلزم معرف نهائي ومفاتيح توقيع محفوظة خارج المستودع.
- AndroidManifest الرئيسي لا يتضمن إذن الإنترنت في النسخة المفحوصة؛ تضاف أذونات الشبكة والصور والإشعارات والخلفية وفق الوظائف. يعالج HTTP المحلي وHTTPS بسياسة منصات صريحة.
- iOS يحتاج إعدادات LAN وBonjour والصور والكاميرا وFace ID والخلفية بحسب الميزات؛ macOS يحتاج استحقاق اتصال الشبكة وملفات المستخدم. لا تُطلب جميع الأذونات عند أول فتح.

### الخلفية والحماية

- iOS يحدد وقت تشغيل BGTask؛ النسخ الفوري بعد كل صورة في كل الظروف ليس معياراً قابلاً للضمان. يستخدم URLSession للنقل الطويل، ويُختبر تعليق التطبيق وإغلاقه قسرياً واستخدام كوكي منتهية. المصادر: [استراتيجيات الخلفية](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)، [نقل الملفات في الخلفية](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background).
- Android يفرض حدوداً على خدمات `dataSync` عند استهداف Android 15 فما بعده؛ استمرار خدمة foreground بلا حد زمني غير صالح. تحفظ نقاط الاستئناف وتُستخدم آلية النقل المناسبة لحجم المهمة وإصدار النظام. المصدر: [حدود خدمات foreground](https://developer.android.com/develop/background-work/services/fgs/timeout).
- محركات الخلفية والمشغل لا ترث معترضات Dio تلقائياً. تمرر إليها المصادقة وسياسة TLS وتُلغى طلباتها عند الخروج، مع اختبار مستقل.
- تختلف قدرات `local_auth`؛ Windows Hello لا يضمن فرض `biometricOnly`. عند غياب المصادقة البيومترية يستخدم قفل الجهاز أو سياسة PIN موثقة. المصدر: [local_auth](https://pub.dev/packages/local_auth).
- دعم macOS في workmanager لا يعني استمرار المهام بعد إنهاء التطبيق، ودعم Windows لا يُفترض من اسم الحزمة. المزامنة أثناء تشغيل تطبيق سطح المكتب تكفي للشريحة الأولى؛ الاستمرار بعد الإغلاق يحتاج قرار منتج وتنفيذاً مستقلاً. المصدر: [workmanager](https://pub.dev/packages/workmanager).

يُفسَّر هدف 100ms كتغذية راجعة للتفاعل المحلي، مع قياس زمن جلب البيانات منفصلاً. سلاسة 60fps تحتاج عادة ميزانية إطار تقارب 16.7ms. هدف RAM البالغ 180 MiB يُقاس على أجهزة وصيغ محددة ويُراجع بعد تجربة الوسائط؛ لا يُعتبر ضماناً لكل دقة فيديو على كل جهاز.

تشمل الاختبارات Unit لعقود البيانات ومحرك النقل، وWidget للحالات الحساسة، وتكامل Flutter/Go بحسابات وتجهيزات مؤقتة، واختبارات أجهزة للخلفية والمصادقة. تظل Zero Telemetry والخطوط المحلية شرطاً؛ تُراجع أي شبكة خارجية صادرة من الحزم أثناء التشغيل.

### نتائج التحقق أثناء هذه المراجعة

- `go test ./pkg/localauth ./route/v1 .`: نجح في الحزم الثلاث. هذه عينة المصادقة وواجهات الملفات والجذر، وليست تشغيل `go test ./...` أو إثباتاً لأجهزة الإنتاج.
- `flutter test` في الفحص الأول: نجح اختبار `Counter increments smoke test` الوحيد وقت التشغيل؛ يغطي القالب الافتراضي السابق. بعد إضافة الشاشات وتغيير نقطة الدخول يلزم اختبار السلوك الجديد، ولا يُنقل نجاح القالب إلى النسخة الجديدة.
- `flutter test --no-pub` في الفحص اللاحق: فشل تحميل الاختبار بسبب خطأي توافق المظهر المذكورين أدناه. هذه هي نتيجة الاختبار الأحدث التي جرى الحصول عليها أثناء المراجعة.
- `flutter analyze --no-pub` في الفحص اللاحق: أبلغ عن 49 ملاحظة، منها خطآن `argument_type_not_assignable` في `lib/core/theme/app_theme.dart` عند السطرين 30 و124: استخدام `CardTheme` حيث يتوقع SDK `CardThemeData`، وبقية الملاحظات تحسينات lint. تسجل في مهام التأسيس؛ لم تُعدل الشيفرة ضمن عمل التحليل.
- تغيرت بعض ملفات التطبيق أثناء المراجعة، لذلك تعاد اختبارات خط الأساس بعد تثبيت نسخة العمل وقبل تنفيذ أول مرحلة.

## 11. قائمة البدء العملية

1. تثبيت نسخة العمل الحالية للتطبيق والخادم وتسجيل التعديلات الموجودة دون استبدالها، مع إضافة إدارة إصدار للتطبيق.
2. معالجة خطأي المظهر ومراجعة اختبار القالب ليتحقق من نقطة الدخول وسلوك التطبيق الجديد، وإعادة `flutter analyze` و`flutter test` في مهمة التنفيذ، ثم استكمال متطلبات بناء Android وWindows.
3. إنشاء ملحق `standalone-client-api` بعينات جلسة وإعدادات ومجلد ونص وسلة ورفع فعلي واختبارات توافق.
4. حسم هوية الحساب الثابتة في الجلسة، وحدود النظام الأدنى، وسياسة TLS المحلية.
5. تنفيذ شريحة صغيرة: عنوان خادم يدوي → دخول → قراءة الإعدادات → عرض مجلد المستخدم → رفع ملف صغير → خروج وتنظيف.
6. تجربة ملفات كبيرة ومشغل فيديو مصادق عليه مبكراً، وفحص مسار الخلفية على iOS قبل تثبيت مكتبات الوسائط والنقل.
7. بناء بقية الشاشات فوق المستودعات الفعلية؛ تبقى البيانات التجريبية محصورة في معاينات واختبارات التطوير.

المخرجات التالية المقترحة بعد اعتماد اتجاه التنفيذ: عقد API موثق، backlog مرتب بحسب المراحل، ثم شريحة اتصال وملفات يمكن تجربتها على خادم اختبار معزول.
